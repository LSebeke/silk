# Silk v1 spec

Silk is a FoundryVTT module for DSA5. The GM maps a Story on a World Canvas. Story Elements map to Foundry documents, World State flows both ways, Adventures branch from and merge back into a Canon, and the GM Reveals content and works the canvas quickly mid-session.

- **Vocabulary**: [`GLOSSARY.md`](../../GLOSSARY.md). Capitalised terms below are glossary terms.
- **Decisions**: [`docs/adr/`](../adr/). The planning map is [Map: Silk v1 spec](https://github.com/LSebeke/silk/issues/1). Each section links the tickets that hold the reasoning.
- **Target**: Foundry v14 (≥ 14.364, verified 14.369) + dsa5 ≥ 8.x (verified 8.1.10). Self-hosted Foundry only; hosted services are best effort.

---

## 1. Scope

**In v1:** everything below.

**Out of scope**, planned for v2 ([Map: Silk v2 spec](https://github.com/LSebeke/silk/issues/62)):
- Merging main into or out of a running Adventure, and merges between branches.
- Reverting a confirmed merge.
- LLM-driven import of written adventures (it builds on the command API).
- Scene setup tools: music via Tabletop RPG Music, and a curated, tagged catalog of battle maps and mood images for Scene Presets.

**Out of scope**, future/later:
- Per-player Reveal (v1 Reveals to the whole party).
- Player-side travel/reveal UI. The read-only Player Canvas *is* in v1.
- Custom Element Classes, custom journal templates, custom Scene Presets.
- Editing the Canon outside Foundry.

**Out of scope**, no plans yet:
- Standalone app and Obsidian plugin ([ADR 0001](../adr/0001-foundry-module-platform.md)).
- Game systems other than DSA5.
- Multi-GM collaboration.
- Hosted Foundry services (The Forge etc.).

## 2. Architecture and stack

Source: [Tech stack, build and test strategy](https://github.com/LSebeke/silk/issues/23).

- **Language/UI**: strict TypeScript and Svelte 5 for every window, with no Handlebars. A shared `SvelteApplication` base on ApplicationV2 mounts in `_replaceHTML`.
- **Canvas**: Svelte Flow (`@xyflow/svelte`). dagre is used for Untangle. No v1 feature needs ELK; if it is ever added, it must be lazy-loaded (EPL-2.0/GPL-3.0). Cytoscape is not used. See [Canvas library for a 500-node story graph](https://github.com/LSebeke/silk/issues/4) and [Canvas fast-drag performance](https://github.com/LSebeke/silk/issues/17).
- **Build**: Vite lib build into one ES module plus CSS, and lazy chunks for the canvas and merge UI. npm, single package, module id `silk`. `fvtt-types` is pinned to v14. DSA5 types are hand-written for the adapter's fields only.
- **Layers**:
  - **Core** (pure, no `foundry`/`game` globals): Canon model, snapshots, 3-way merge, Revelation Map, sync rules, Canvas Filters/Focus View, Creation Pipeline, command registry.
  - **Foundry/DSA5 adapter** (injected): hooks, doc writes, ownership, sockets, FilePicker, DSA5 field mapping and sheet section labels.
  - **UI**: Svelte, talks to the core through stores.
- **Every UI action is a command** ([ADR 0003](../adr/0003-every-ui-action-is-a-command.md)):
  - Buttons, keys and menus only invoke registry commands.
  - The registry is exposed at `game.modules.get('silk').api`, documented and unstable in v1.
  - Every interactive element has a stable `data-silk-*` attribute.
  - A dev/test-only MCP server wraps the API.
  - Each feature adds its commands first and its UI second.
  - **Naming**: dot-namespaced `area.verb`. Each command takes one args object and returns a Promise.
  - **Registry entry**: `{ name, title, keys?, available(ctx), run(args) }`. `title`, `keys` and `available` drive the keybindings, context menus and palette.
  - The v1 catalogue is §15. Implementers may add commands, but renaming one requires a spec update.
- **Pop-out windows**: v14 `detachWindow`. Detached windows don't restore after a reload, so Silk persists window position and detached state in client settings and re-detaches the window itself. The canvas binds to the app's own `ownerDocument`.
- **Flags**: `flags.silk` holds ids only. The one exception is `silk.img` (the real image behind the hood, see §8). Silk tags its own writes so its hooks ignore them.
- **Dev loop**: `vite build --watch`, with `dist/` symlinked as `Data/modules/silk`, then F5. No HMR.

## 3. Domain model

```
Canon (one shared history, Data/silk/<id>/)
 ├─ main ── Commits
 ├─ Adventures (branches off main; each carries a Campaign label)
 └─ Campaigns (Revelation Map, open/closed)
World (Foundry world) ── bound to one Canon for life ── exactly one Checkout (main or one Adventure)
```

- One Canon holds many Campaigns. A Campaign is a sequence of Adventures with one group.
- Parallel Adventures need separate Worlds.
- Story Elements don't belong to Campaigns. Only Reveals (the Revelation Map) and Player Notes' authoring Campaign do.
- Source: [Canon storage and Adventure branch model](https://github.com/LSebeke/silk/issues/9), [Adventure lifecycle: checkout, commits, sync](https://github.com/LSebeke/silk/issues/14).

## 4. Element Classes

Source: [Element Class catalogue](https://github.com/LSebeke/silk/issues/6), [Reveal rework after in-app checks](https://github.com/LSebeke/silk/issues/16).

**Common to every class**: title (= doc `name`), image (= `img`), Tags (GM only, never shown to players), Info Blocks, Revealed state, Node position. A class field exists only if it carries a mechanic. Descriptive content lives in Info Blocks.

| # | Class | Foundry doc | Class fields | Status | Default Info Blocks |
|---|---|---|---|---|---|
| 1 | Person | Actor `npc` + Companion Journal | `merchantType` (mirrors `system.merchant.merchantType`) | alive/dead ↔ DSA5 `dead` condition | Appearance, Personality, Secrets |
| 2 | Creature | Actor `creature` + Companion Journal | – | alive/dead | Appearance, Description |
| 3 | Player Character | Actor `character` + Companion Journal; **Adopt only, never created by Silk** | – | – | Description |
| 4 | Location | JournalEntry | optional Overview Scene | – | Description, Secrets |
| 5 | Faction | JournalEntry | – | – | Overview, Secrets |
| 6 | Item | Item (any DSA5 subtype) + Companion Journal | – | – | Description, Secrets |
| 7 | Event | JournalEntry | Event Scene + Scene Preset | planned/happened/skipped | Setup, Outcome |
| 8 | Quest | JournalEntry with one `dsaquestlog` page = one quest | – | open/done/failed ↔ quest `status` 0/1/2 | Hook, Resolution |
| 9 | Note | JournalEntry, no layout | – | – | Description |

(The # column is the digit key that creates the class, §10.3.)

- **Info Block** = one text `JournalEntryPage`, page name = block name. Default blocks start empty and can be deleted.
- **Companion Journal**: holds an Actor/Item element's Info Blocks. It is linked to the doc both ways by flag.
- **Journal layout** (journal classes): page 1 is the Silk-managed **Cover** image page (element image). Next come the Info Block pages, then the Silk-generated **Connections** page (§5), then the **Player Notes** page category (§9).
- **Class change**: allowed only to another class backed by the same kind of Foundry doc (e.g. Note → Location).
- **"Known" is never a Status**, it is the Revealed state. "Visited" is derived (§5). Item ownership is the **owns** Connection.
- **Event Scenes**:
  - Each Event owns its own Foundry Scene. Its journal shows a Scene link (GM only, click = view) and an **Activate** button.
  - Silk generates the Scene config from the Scene Preset. The GM draws walls and places the map by hand.
  - Presets:

    | Preset | Setup |
    |---|---|
    | Travel | hex grid, no vision or fog |
    | Battle | square grid, token vision, walls, fog |
    | Narrative (default) | mood image as background, plus a box holding the tokens of the actors present, which start hidden |
    | Overview | map, no grid or vision; Location only |
- **Quest specifics**:
  - The quest is created with `visible: false` and `audience: 0` (Party). Quest `title` ↔ element title.
  - On Materialize, its journal is registered in the DSA5 `questlogJournals` setting.
  - Each Info Block is a text page plus a `linkedPages` entry whose `visible` mirrors that block's Reveal.
  - Native `summary`/`details`/`objectives`/`gmNotes` stay DSA5-owned and GM-written. Silk warns that they become visible on element Reveal.
- **DSA5 `information` items** (roll-tiered tactical knowledge) stay a Game System mechanic, unrelated to Info Blocks.

## 5. Connections

Source: [Behavioural Connection types](https://github.com/LSebeke/silk/issues/7), amended by [World State capture and sync rules](https://github.com/LSebeke/silk/issues/8).

### Behavioural Connections

| Type | Source → Target | Cardinality | Behaviour |
|---|---|---|---|
| **owns** | Person/Creature/PC → Item | ≤1 owner per Item | Both Materialized → the Item is embedded in the actor's inventory. That embedded copy *is* the Item's materialization. An unowned Item Materializes as a world Item. |
| **present at** | Person/Creature → Event | many–many | Symmetric with tokens on the Event Scene (§7). Tokens are placed **hidden**: in the box for Narrative, stacked at an edge for Battle/Travel. PCs are never sources. |
| **located in** | Item/Location → Location | ≤1, no cycles | Drives the "show contents" filter and the "visited" roll-up to containing Locations. |
| **takes place at** | Event → Location | ≤1, optional | Location is "visited" when an Event there is `happened`. |

- An Item is **owns xor located in**. A new conflicting Connection replaces the old one.
- The canvas offers only the types valid for the class pair.
- **Default type on create-from**:

  | From → new | Default type |
  |---|---|
  | Person/Creature → Item | owns |
  | Event → Person/Creature | present at |
  | Location → Location/Item | located in (the new element sits inside the origin) |
  | Location → Event | takes place at |
  | anything else | free-form |
- **Flip** (one click) is offered only when the reversed pair is valid.

### Free-form Connections
- **Directed** (A → B; the label is a verb phrase, "A loves B") or **mutual** (C — D; the label is a plural predicate, "C and D are friends").
- Opposing feelings are two directed Connections.
- One action cycles A→B / B→A / mutual. *member of* and *part of* stay free-form.
- **Rendering**: directed = arrowhead, mutual = none. Several Connections between the same pair are drawn as separate curved, labelled edges. Edges attach on the side facing the other Node.

### In journals
- Every Connection renders as a generated, read-only sentence on the **Connections** page of both endpoints. Behavioural types use fixed localised phrases (DE/EN).
- Players see only Revealed sentences (§8).

## 6. Materialize, Unmaterialize, Delete, Adopt

Source: [Materialize trigger and unmaterialize/delete](https://github.com/LSebeke/silk/issues/21), [Importing Foundry docs as Story Elements](https://github.com/LSebeke/silk/issues/22).

### Materialize
- **Mode**: a per-World GM setting, **immediate** (default) or **on demand**. Ghost = a Node that isn't Materialized in this World. Materialized Nodes render solid, Ghosts faint.
- **Immediate**: the doc is created when the Creation Pipeline finishes its name step. That includes the Companion Journal and, for Events, the Event Scene (Narrative by default).
- **On demand**:
  - Explicit: context menu, `m`, multi-select.
  - Implicit, with a toast: Reveal, a new **present at**/**owns** with a Materialized element, opening the sheet, Event Scene activation.
- **No retroactive Materialize** on a mode switch or checkout.
- **Materialize visible**: bulk action over every Ghost rendered under the current Canvas Filters and Focus View, offscreen included. It skips Player Characters and asks for confirmation with a count first.
- Foundry's `migrateData` upgrades stored doc data on Materialize (§13).

### Unmaterialize
A GM action, never blocked.
1. Snapshot the full doc data (sheet, pages, Event Scene incl. walls) into the working copy.
2. Delete the doc, its Companion Journal, its Event Scene and its tokens.
3. The element stays as a Ghost with its Connections. Its Revelation Map entry is kept, so Materializing again restores ownership.

A Revealed element warns that players will lose access.

### Foundry-side deletion
- **The doc is deleted in Foundry** → always Unmaterialize, never element deletion. The snapshot comes from the delete hook. If the hook was missed, reconcile restores the last Commit's snapshot and flags the element "restored from <commit>".
- **The Companion Journal is deleted** → it is restored from the last Commit, with a warning that uncommitted Info Block edits are lost.
- **The Event Scene is deleted** → the Scene link is cleared. The Event shows "no Scene" with **Create Scene** / **Restore from last commit**. **present at** Connections stay.

### Delete element
Canvas only.
- **Element created by Silk**: confirm, then delete its Connections, Foundry docs and Revelation Map entries.
- **Adopted element**: the confirmation offers **Keep Foundry doc** (default: removes the Silk id, Connections and Revelation Map entries) or **Delete everything**.
- The only undo is discarding uncommitted changes.

### Adopt
Adopt makes an existing Foundry doc a Story Element. The doc stays where it is and is Materialized from the start.
- **Ways in** (each ends in the Creation Pipeline with class and name pre-filled):
  - Drag from the sidebar or a compendium onto the canvas. Dropping onto a Node also labels a Connection.
  - "Adopt into Silk" in the sidebar context menu and on the sheet header.
  - "Adopt folder into Silk" (bulk). It skips the pipeline; one confirmation lists the docs and their inferred classes.
  - Inventory item context menu on an actor sheet. It asks "Also adopt *actor*?": yes adopts both and adds **owns**. If the actor is adopted later, reconcile adds **owns**.
- **Class inference**:

  | Foundry doc | Class |
  |---|---|
  | Actor `character` | Player Character |
  | Actor `npc` | Person |
  | Actor `creature` | Creature |
  | Actor `group`/`vehicle` | refused with a toast |
  | Item | Item |
  | Journal with a `dsaquestlog` page | Quest |
  | other journal | class box with Note pre-selected; bulk Adopt makes them Notes |
  | Scene | GM picks: a new Event owning it, or a Location with it as Overview Scene. The Scene config is untouched, no Preset applied. |
- **Content**: journal pages become Info Blocks as they are, with no default blocks. An Actor/Item gets an empty Companion Journal. Only the Silk id flag is written to the doc.
- **Compendium entries** are imported into the World by a normal Foundry import, and the copy is adopted.
- **Duplicates**:
  - A doc with a Silk id isn't adopted again; its Node flashes and is selected.
  - A duplicated doc has its copied Silk id stripped.
  - If `_stats.compendiumSource` matches a Canon element, the GM is asked "use this doc for *X*" (Materializes that Ghost) or "create new".
- **Ad-hoc docs**: no prompt during play. **End Play Session** lists the top-level Actors, Items, Journals and Scenes created since the last Commit that aren't Story Elements (embedded items and tokens excluded). Each row has **Adopt** or **Ignore**, and an ignored doc never reappears.
- **Placement**:
  - A drop lands at the drop point.
  - Other single Adopts land at the viewport centre.
  - Bulk Adopts land as a selected grid at the centre, ready for `u`.
  - A folder tree becomes the same tree of nested Visual Groups.
- **Connections** inferred on Adopt: only **owns** (from inventories, between Story Elements only) and **present at** (from tokens on Event Scenes). No Connections are inferred from `@UUID` links in text.
- **Reveal**: a doc players can already see counts as Revealed. Its ownership is unchanged.

## 7. World State sync

Source: [World State capture and sync rules](https://github.com/LSebeke/silk/issues/8), [Foundry module APIs for Silk](https://github.com/LSebeke/silk/issues/2), [DSA5 system data model](https://github.com/LSebeke/silk/issues/3).

- **Source of truth**:
  - For a Materialized element, the **Foundry doc is truth**: title = `name`, image = `img`, Info Blocks = pages, class fields via the adapter.
  - Canvas edits write through to Foundry immediately, with no draft.
  - Silk itself stores only what Foundry has no field for: Connections, Tags, Event happened, layout.
  - Each field has one owner, so there are no live two-sided conflicts.
- **Non-Materialized** elements are edited in the working copy only.
- **Capture**: any change to a Materialized doc's versioned fields is World State, plus the Story effects derived from it. Player edits (PC sheet, inventory) count the same as GM edits. There is no whitelist.
- **Dead** ↔ dsa5 `dead` condition (`actor.hasCondition('dead')`), both ways, **linked actors only**. LeP ≤ 0 alone changes nothing. Other conditions are just versioned actor data.
- **owns** follows the Item's Silk id. The id moves only when the original doc is deleted in the process (a move between actors). Copies get no Silk id. When the copy leaves the actor, the Connection moves or is deleted.
- **present at ↔ tokens**, Event Scenes only:
  - Placing a token creates the Connection if it's missing.
  - Removing the actor's **last** token on that Scene deletes the Connection.
  - Creating the Connection adds one hidden token. Deleting it removes all of the actor's tokens, hidden or not.
  - Tokens are never moved between Scenes.
  - Tokens on non-Event Scenes are ignored.
- **Happened**: set automatically when the Event Scene is first Activated. The GM can undo it.
- **No auto-promotion**: ad-hoc docs stay plain Foundry data until Adopted (§6). Ad-hoc Items are versioned as part of their actor.
- **activeGM gate**: hooks fire on every client, so Silk's follow-up writes run only on `game.users.activeGM`. With no GM online, Silk doesn't react.
- **Reconcile on load** (GM): recompute everything derived (owns, Dead, Revealed, present at, missing docs) from Foundry. Missed hooks are never replayed.
- **Ignored**: combats, chat, playlists, macros, users, settings, fog, folders/sort, ownership (handled by Reveal), unlinked-token deaths, tokens on non-Event Scenes.

## 8. Reveal

Source: [Reveal mechanics](https://github.com/LSebeke/silk/issues/10), superseded in part by [Reveal rework after in-app checks](https://github.com/LSebeke/silk/issues/16) and verified by [Verify OBSERVER entry with NONE pages and Cover](https://github.com/LSebeke/silk/issues/19).

- **Audience**: the whole party (all non-GM users) of the Campaign of the checked-out Adventure.
- **Under the main Checkout** (Canon edit mode) there is no Campaign:
  - Reveal commands are unavailable, with the hint "start an Adventure to Reveal".
  - Ownership stays as the last Adventure left it.
  - The Revealed filter reads the World's current ownership.
  - Player View is frozen.
- **Only Materialized elements** can be Revealed. Revealing a Ghost Materializes it first, regardless of the mode.
- **Defaults**: Silk-created pages get explicit player ownership **NONE**, not INHERIT.
- **What each Reveal does**:

  | Reveal | Journal element (Location, Faction, Event, Quest, Note) | Actor/Item element |
  |---|---|---|
  | **Element** | entry **OBSERVER** + Cover page OBSERVER. Info Block pages stay NONE. Quest: also `visible: true`. | doc **LIMITED** (sidebar + limited sheet, hooded image). Companion Journal stays NONE. |
  | **Info Block** | page OBSERVER (+ the element Reveal). Quest: its `linkedPages.visible: true`. | page OBSERVER. The Companion Journal becomes OBSERVER on its first Revealed block, Connection or Player Note. |
  | **Connection** | Silk stores the Connection's Revealed flag. The sentence appears on both endpoints' Connections pages, which go from NONE to OBSERVER on their first Revealed Connection. Both endpoints get an element Reveal. If an endpoint must stay hidden, that belongs in a Secrets block. | same |

  Revealing a part Reveals its element(s), but nothing more.
- **Appearance** (Person/Creature):
  - Until the Appearance block is Revealed, `img` and the prototype and placed token textures show the **hooded image**, and the real image waits in `flags.silk.img`.
  - The hooded image is one default shipped with Silk, overridable by a world setting (not per actor).
  - Token `displayName` is OWNER before element Reveal and HOVER after.
- **Hidden tokens** (present at) are plain Foundry `hidden`. Un-hiding a token Reveals nothing.
- **Delivery**: Reveal is silent by default. **Show to players** = Reveal if needed + a forced `Journal.show` popup.
- **Un-reveal** reverses everything above, with no confirmation. It also hides the element's Player Notes, which are kept and come back on re-Reveal.
- **Truth**: ownership in the World. It is mirrored in the Campaign's **Revelation Map** (§11.5):
  - Every Reveal or un-reveal writes to the map.
  - Checkout and Materialize apply the map to ownership.
  - Reconcile on load repairs drift; ownership wins.
- **Sidebar discoverability**: Silk files docs into per-Element-Class folders plus a "Silk Companions" folder. Empty-for-player folders don't show. The Player Canvas is the main way in.
- **Controls**:
  - Node eye toggle (top right of the card).
  - Right-click on Nodes and Connection edges: Reveal / Reveal Appearance / Show to players.
  - `r` with a y/n confirm.
  - **Element Detail** window (double-click a Node): eye toggles for each Info Block and Connection, the same context menu, writes through to Foundry.
  - Silk header buttons on journal sheets and actor/item sheets.
  - No Token HUD controls.

## 9. Player Canvas and Player Notes

Source: [Player canvas and Player Notes](https://github.com/LSebeke/silk/issues/18), [Spoiler secrecy threat model](https://github.com/LSebeke/silk/issues/15).

### Player Canvas
- **Data**: the **Player View** world setting holds Revealed Node ids + Canon positions and Revealed Connections + labels. The activeGM writes it on every Reveal or move. Content comes from world docs the player can see. Players never read Canon JSON.
- **Node**: class colour, name, Cover (hooded until Appearance is Revealed). No Status, no Info Blocks. Clicking opens the Foundry doc (journal entry, or the LIMITED sheet + Companion Journal).
- **View**:
  - Canon positions. Unrevealed Nodes and their Connections are omitted, and there are no Visual Groups.
  - Read-only, pan/zoom only. View state is per client.
  - No Focus View, Filters, Status or Reveal UI.
- **Entry**: the same Silk scene-control button as the GM's.

### Player Notes
- A party notebook. Any player can create a note on any Revealed element. All players see every note, and any player or the GM can edit or delete any note.
- Players can't create Nodes or Connections, and Player Notes can't go on Connections.
- **Creation**: socket → activeGM creates the page under the **"Player Notes"** page category of the element's journal or Companion Journal. With no GM online, notes can't be created.
- **Cross-Campaign**:
  - A note records its authoring Campaign and is auto-Revealed in that Campaign's Revelation Map.
  - It is versioned and merged into the Canon like any Info Block.
  - Other Campaigns get it as a NONE block, shown only if their GM Reveals it.
- **Convert to GM Info Block** (one-way):
  - The page leaves the category and players lose edit rights (page → NONE, or OBSERVER if Revealed).
  - It stays Revealed in its Campaign, and the authoring Campaign tag is dropped.
- The GM can view, edit and reposition Player Notes.

## 10. GM canvas

Source: [Canvas interaction prototype](https://github.com/LSebeke/silk/issues/11), [Canvas fast-drag performance](https://github.com/LSebeke/silk/issues/17), [Canvas Filters and render budget](https://github.com/LSebeke/silk/issues/20), [Focus View prototype](https://github.com/LSebeke/silk/issues/12). The prototype branches are references, never merged: `prototype/canvas-interaction`, `prototype/canvas-fast-drag`, `prototype/focus-view`.

### 10.1 Window
- An ApplicationV2 window (detachable), opened from a Silk scene-control button. The canvas shows the whole web of the Checkout. The canvas is the editor.
- Per-World, unversioned view state: pan/zoom, last view, active Canvas Filters, Focus Pins. Reopening restores the last view.

### 10.2 Cards and zoom
- **Three zoom levels**: full card → big title → coloured block with title.
- **Full card**: image, title, Status chip, eye toggle, Focus Pin button, Connection Points.
- **Connection Points** have three kinds: outgoing, incoming, mutual. They sit on all four sides, are always visible at full zoom, and are larger than in the prototype.
- **Detail drop while moving**:
  - While the viewport pans or zooms, every card becomes a blank block in its class colour (paint only, no reflow), and Connections and their labels are hidden.
  - Full detail returns 150 ms after the viewport stops.
  - Client setting, on by default. No automatic switching based on measured fps.
- Don't use `onlyRenderVisibleElements`: it makes fast drag worse.

### 10.3 Creating
The **Creation Pipeline** (every way of creating ends here):
1. Class selection box: searchable, opens at the spot.
2. Name field, focused with the cursor placed.
3. If created from a Node: the Connection editor, focused on its label.

A Connection created on its own opens its editor straight away.

- **Mouse**:
  - Drag out a Connection from a Connection Point (its kind sets the direction). The class box opens where it's dropped.
  - Right-click the canvas → class box → standalone Node. **No double-click create.**
  - Node context menu: actions, plus a class box to the right of them that creates a connected Node.
  - Palette: drag a class onto the canvas, or onto a Node (the Node highlights as the connect target).
- **Keyboard**:

  | Key | Action |
  |---|---|
  | `1`–`9` | Create a Node of class #n (§4); connected to the selected Node if any. Default outgoing; Shift/Ctrl/Alt pick another direction/type. |
  | `c` | Connect: search for the target; the default entry "New Node" asks direction + class, then runs the pipeline |
  | `Tab` / `q` | On a selected Connection: cycle direction / cycle type |
  | `F2` | Rename a Node / edit a Connection label |
  | `g` | Group the selection into a Visual Group |
  | `s` | Toggle Status, y/n confirm (default n) |
  | `r` | Reveal, y/n confirm (default n) |
  | `m` | Materialize |
  | `p` | Pin/unpin Focus |
  | `u` | Untangle (≥2 selected) |
  | `Ctrl+F` | Search (only while the canvas window has focus) |
- **Status and Reveal** are each reachable three ways: a card chip/👁, the context menu, and a key.

### 10.4 Visual Groups
- Labelled frames that hold Nodes. They nest without a depth limit.
- A dropped Node joins the innermost frame.
- Untangle grows all enclosing frames.
- They are Canon layout data (§11).

### 10.5 Canvas Filters
- **Dimensions**: Element Class, Status, Revealed (the Adventure's Campaign; under main, current ownership), Materialized vs Ghost, Tag, Visual Group (includes nested groups), N-hop distance, "show contents" (located in). There is no Campaign dimension.
- **Logic**: OR within a dimension, AND across dimensions. No boolean builder.
- Filtered-out Nodes are **not rendered**, never dimmed. A visible Node with Connections to hidden Nodes shows a **"+N" badge**; clicking it shows those neighbours.
- An always-visible **chip bar** lists active filters, "N of M shown", and a one-click clear.
- No named presets.
- **Render budget**: a non-blocking warning when more than 1000 Nodes are visible. The threshold is a client setting.

### 10.6 Focus View
- Focus View = the N-hop filter, ANDed with the others. One N, default 2.
- **Seeds**: the active Scene and its tokens' elements, plus the current selection (a union for multi-select). The selection part is temporary: a new selection moves it, and deselecting collapses it.
- **Focus Pins** are always shown, but are not seeds. With no Scene and no linked elements, only pins show, plus a hint.
- **Camera**:
  - Nodes always sit at Canon positions. Hidden Nodes vanish instantly, and only the camera animates (~450 ms ease).
  - Scene change → the camera fits the new focus.
  - Selection, badge or pin change → the camera pans only if newly shown Nodes are offscreen, and never zooms in.
  - The camera holds while Shift is down; skipped moves are dropped.
  - "+N" extras clear only on Scene change or via the chip bar.

### 10.7 Untangle
- Needs ≥2 selected Nodes. Triggers: selection toolbar, context menu, `u`.
- dagre lays out left-to-right over the selected Nodes and the Connections between them, centred on the selection's centroid. Unselected Nodes never move.
- The result applies as one ~450 ms tween. Frames grow to fit.
- The positions go into the working copy, and one Ctrl+Z undoes the whole Untangle.

### 10.8 Search
- A button and `Ctrl+F`. Results come in this order: Nodes, Tags, Info Block text. Ghosts are included; Connection labels are not.
- A Tag result expands into its elements.
- Jumping selects the Node, so Focus View expands to it. If a filter hides it, it is shown temporarily with a "filtered" marker until deselected. A newly created Node that filters would hide is treated the same way.
- `c` and the palette share Search's matcher and index.

## 11. Canon, branches and merge

### 11.1 Storage
Source: [Canon portability and on-disk format](https://github.com/LSebeke/silk/issues/25), [Branch/merge storage for JSON documents](https://github.com/LSebeke/silk/issues/5).

- Custom per-field 3-way merge over content-addressed JSON. No isomorphic-git, Automerge or Yjs.
- Written via `FilePicker.upload('data')` to `Data/silk/<canon-id>/`. The id is a **random 128-bit** value ([ADR 0002](../adr/0002-spoiler-secrecy-casual-player-only.md)).

```
canon.json                          manifest: id, name, formatVersion, createdWith
objects/<ab>/<hash>.json            immutable blobs, one per record
commits/<hash>.json                 parents, label, date, author, tree (record id → blob hash)
refs/main.json
refs/adventures/<id>.json           head, name, Campaign id, base commit
campaigns/<id>/campaign.json        id, name, closed, createdAt, formatVersion; unversioned, overwritten in place
campaigns/<id>/revelation-map.json  unversioned, overwritten in place
```

- **Records**: element, Connection, sheet (full Actor/Item doc data), Event Scene, layout group.
- **Write order**: a Commit uploads only changed blobs, then the commit, then the refs last. A crash leaves only orphans.
- **Format versioning**:
  - An integer `formatVersion` sits on the manifest and on every blob and commit.
  - Older versions migrate on read, in memory, so hashes stay valid. Writes use the current version.
  - A newer version than the installed module opens the Canon **read-only** with an "update Silk" warning.

### 11.2 What is versioned
Source: [Canon storage and Adventure branch model](https://github.com/LSebeke/silk/issues/9), [Adventure lifecycle: checkout, commits, sync](https://github.com/LSebeke/silk/issues/14).

- **Versioned**: Story Elements (fields, Status, Info Blocks, Tags), Connections, World State, full Actor/Item doc data (system data, embedded Items, Active Effects; not ownership, folder, sort, token placement), Event Scenes incl. tokens and walls, **layout** (Node positions, Visual Groups).
- **Per Campaign, unversioned**: Revealed state (the Revelation Map, §11.5), never part of the Canon history.
- **Per World, unversioned**: pan/zoom, last view, Canvas Filters, Focus Pins/View, ignored ad-hoc docs, merge drafts.
- **Not exported**: the World-only data above, plus ownership, folders, playlists, macros and tables.
- Blobs keep `_stats` (core + system version). Silk never migrates DSA5 data itself. Merges compare post-migration data.

### 11.3 Lifecycle
- **Binding**: a World is bound to one Canon for life. A fresh World has no Checkout until the GM picks or creates a Canon.
- **Checkout**: exactly one, main (Canon edit mode) or one Adventure. It changes only when an Adventure ends, then falls back to main.
- **Working copy** lives in the World:
  - Materialized docs hold their own data.
  - Everything else (non-Materialized elements, Connections, Tags, layout) lives in the **Silk Working Copy**: a hidden JournalEntry (player NONE, in a "Silk (internal)" folder).
    - One record per `flags.silk.records.<id>`, so updates are diffs, not whole-value broadcasts like world settings.
    - It also holds the merge draft and the ignored ad-hoc docs.
    - It travels with world exports. Players' clients receive it, which ADR 0002 accepts.
    - Only activeGM writes it.
  - Small view state (pan/zoom, last view, filters, Focus Pins) lives in world settings.
  - Nothing is written to `Data/silk/` until a Commit.
- **Start Adventure**: only from a clean main. It branches from main's head, with a name and an open Campaign (pick or create). No branching from older commits.
- **Commits** happen on the **End Play Session** button (which also lists unadopted docs, §6), on manual commit, and automatically before a merge. No timed autosave.
  - History is linear and viewable (label + date).
  - The only undo is "discard uncommitted changes" (reset to the last Commit).
- **Sync**: merges into main never flow into a running Adventure.
- **Canon edit mode**: Commits write straight to main. On load, if main moved: clean → fast-forward (rewrite Materialized docs); dirty → 3-way merge in the merge UI.
- **End Adventure**: Commit → 3-way merge into main → on confirm, one Commit on main, "Merge <Adventure> (<Campaign>)". Materialized docs are rewritten to the result and the World checks out main, keeping its docs. Cancel keeps the Adventure checked out.
- **Abandon**: typed confirmation, irreversible. The World resets to main's head: docs are rewritten, and docs for elements absent on main are deleted. Orphans are left for export-GC (§11.6).
- **Layout merges** never prompt: on a position conflict the incoming side wins. Visual Groups merge per field, and on a nesting cycle the incoming side wins.

### 11.4 Merge UI
Source: [Adventure merge UI](https://github.com/LSebeke/silk/issues/24); prototype `prototype/adventure-merge` is the primary visual reference.

- **Main view**: a canvas diff of the merged result. Nodes and Connections are badged conflict / added / deleted / changed, and "Next conflict" is ⏎.
- **Summary header**: counts, plus the merges the Canon received since the Adventure started.
- **Drawer** (click a Node): a per-field table **Base | Canon now | Adventure → Result**. Click a cell to take it.
- **Auto-merges**: one-sided changes merge automatically. They are listed collapsed and can be overridden per field. Canon-only changes are hidden behind a toggle.
- **Delete vs edit**: one element-level choice (delete, or keep with the edits). Connections of a deleted endpoint follow it.
- **"Write combined text"** is offered only for text fields (Info Blocks, Connection labels). Values, Status and positions are pick-a-side.
- **Attribution chip** (Adventure · Campaign · date) on every field the Canon changed since the Adventure started.
- **Event Scene**: tokens are matched by id, one row each, plus a minimap (base / Canon / Adventure). Walls, lights etc. get count-only summary rows.
- **Sheets**: fields are grouped by section via the adapter's labels. Embedded Items are matched by id.
- **Layout**: shown as outlines and a count, overridable.
- **Draft**: picks persist in the World and can be resumed. Cancel discards the draft.
- **Reuse**: the same window serves Canon edit mode's dirty-load merge (columns "Canon (incoming)" / "This World") and Join Campaigns (§11.5).
- **No undo** in v1. The confirm dialog says so.

### 11.5 Revelation Map and Campaigns
Source: [Reveal mechanics](https://github.com/LSebeke/silk/issues/10), [Revelation Map merge](https://github.com/LSebeke/silk/issues/26).

- **Canon window**, opened from the canvas toolbar:
  - the Canon name and current Checkout;
  - **Adventures**: start, end, abandon, history;
  - **Campaigns**: create, rename, close/reopen, "Join into…";
  - **Canon Backup / Canon Share**: export and import.
- **Revelation Map** = one per Campaign. It holds the ids of Revealed elements, Appearance, Info Blocks, Connections and Player Notes.
  - It is current state only, unversioned, and lives outside the Canon history.
  - Content edits show through; deleted items drop out.
- **Join Campaigns**: from the Canon's Campaign list, choose "Join into…" on the source Campaign and pick the target.
  - Works in any bound World, under any Checkout, at any time.
  - Review happens in the merge UI: columns Target / Source / Result, one row per item, no base column. The default Result is the union, shown as overridable auto-merges, and each item carries a "from <source>" chip.
  - Confirm writes the target map, with no Commit and no undo.
  - A World on a target Adventure applies the ownership right away; other Worlds apply it at their next reconcile.
  - The source's Player Notes are re-tagged to the target.
  - "Close source Campaign" is on by default.
- **Closed Campaign**:
  - Not offered for new Adventures and can't be a join target.
  - Its map is read-only.
  - An Adventure already running still plays out and merges.
  - It can be reopened. Campaigns are never deleted.
- Silk never touches Foundry users.

### 11.6 Portability
Source: [Canon portability and on-disk format](https://github.com/LSebeke/silk/issues/25).

- **Canon Backup** (zip, GM only): everything reachable from refs, all Adventures, all Revelation Maps and Campaigns. Same Canon id.
  - Import when the id exists: if the import's main descends from local main → fast-forward. Otherwise refuse and offer "import as copy" (new id).
- **Canon Share** (zip): any Commit or Adventure head, squashed into one root Commit. No Adventures, Campaigns, Revelation Maps or Player Notes, and no uncommitted work. An Adventure head carries its World State. The import gets a new random id.
- **Assets**:
  - Export bundles every referenced `Data/` file (core/system/module paths skipped), with a SHA-256 per file in the zip manifest.
  - Import skips identical files (hashed via `crypto.subtle`) and reports missing ones.
  - On a path holding different content: a Backup lists the files and overwrites on confirm. A Share writes `<name>.silk-<hash8>.<ext>` and rewrites references.
- **GC**: exports hold only reachable objects, so export → import is the v1 garbage collection (FilePicker can't delete). The export dialog shows the orphan count. Export warns if any bound World has uncommitted changes.
- **Server move** = World folders + Canon Backup. A fresh World binds the Canon, Materializes from it, and rebuilds ownership from the Revelation Map.
- A git repo over the Canon folder works without any feature (documented).

## 12. Spoiler secrecy

Source: [Spoiler secrecy threat model](https://github.com/LSebeke/silk/issues/15), [ADR 0002](../adr/0002-spoiler-secrecy-casual-player-only.md), [Foundry v14 + DSA5 8.x dev instance](https://github.com/LSebeke/silk/issues/13).

- v1 defends against the **casual player** only, through UI gating. Players can read NONE pages, flags and Canon JSON from the console; this is accepted.
- Facts:
  - Foundry sends every journal page to every client.
  - The Data folder is served without auth.
- The Canon lives under an unguessable `Data/silk/<random 128-bit id>/`.
- The README has a **"Spoiler secrecy"** section covering the console leak, Data-folder exposure and FILES_BROWSE.
- A one-time, dismissible GM notice appears on load if any non-GM role has FILES_BROWSE (Trusted has it by default).

## 14. Testing and performance gates

Source: [Tech stack, build and test strategy](https://github.com/LSebeke/silk/issues/23), [Performance verification in CI](https://github.com/LSebeke/silk/issues/27).

- **Unit**: Vitest + fast-check on the core.
- **Integration**: Playwright against headless Foundry with a GM client and a player client, in a fresh scripted world `silk-test-<run>` that is deleted afterwards. `silk-dev` stays manual.
  - Headless launch: `node resources/app/main.js --headless --dataPath=…`.
  - Create a world with POST `/create` `{action:"createWorld"}`, launch it with POST `/setup` `{action:"launchWorld"}`, join with POST `/join`.
  - See [Foundry v14 + DSA5 8.x dev instance](https://github.com/LSebeke/silk/issues/13).
- **Canvas e2e**: Playwright on `data-silk-*`.
- Agents write the code and run the full suite locally. The GM's manual checks are a final smoke test.
- **CI** (GitHub Actions): typecheck, eslint + prettier, unit tests, build, bundle-size check.
- **Perf fixture**: a seeded, deterministic Canon with 500/1000/2000 Elements, shared by all perf tests.
- **Bench**: the fast-pan bench from `prototype/canvas-fast-drag` becomes a dev-only `api` command running on the real canvas in Foundry.

| Target | Check | Where | Fails when |
|---|---|---|---|
| ~500 Elements @ 60 fps | fast pan, 500 fixture, detail drop on, 8 mousemoves/frame, headless Chromium + GPU on the reference machine (GM's RTX 2080) | local, release gate | avg < 55 fps, or p99 frame > 70 ms, or > 15% worse than the last release |
| 1000 / 2000 Elements | same | local, release | reported only |
| Create connected ≤ 2 interactions | core unit test: the Creation Pipeline reaches a connected Element in ≤ 2 user commands per entry point (drag-out, right-click, digit key) | CI | > 2 |
| same | Playwright, counting real input events | local | > 2 |
| Reopen restores last view < 1 s | Playwright, headless Foundry, 500 fixture; open command → viewport restored + Nodes painted; warm, median of 5 | local | > 1 s |
| Bundle size | gzipped entry chunk, PR vs `main`; lazy chunks reported only; diff in the CI log | CI | > 10% growth without the `allow-size` label |

- Results are committed per release as `bench/results/<version>.json` (env string included). That file is the baseline for the next release.
- The GM does a manual pan in Zen/Firefox at release. Headless Firefox is excluded because it exaggerates compositing costs.

### Release and versioning
- A git tag triggers a GitHub Release with a manifest URL. The Foundry package site comes later.
- Each release targets one Foundry/DSA5 pair, with accurate `compatibility` and `relationships` in `module.json`.
- Old releases stay installable.
- Backports go to a maintenance branch, for data-loss and spoiler-leak bugs only.
